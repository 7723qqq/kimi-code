# 上游 2.7.0 整仓对齐与 Desktop Bun 化

## 目标与使用者

将本 fork 对齐到上游正式发布的 Kimi Code 2.7.0，范围包含新增 Desktop，而不只是 CLI 版本号。面向现有 CLI、SDK、Web、ACP、VS Code 使用者，以及希望在本仓开发和运行桌面端的使用者。

用户已确定“整仓含 Desktop”，并补充“桌面端也应当使用 bun”。本规格将后者落实为 Bun 安装、开发、构建、测试及代理后端运行；保留上游 Electron 窗口载体，不把 Electron 内嵌 Node 环境误称为 Bun，也不要求另装外部 Node。

## 固定来源

- 正式标签：`@moonshot-ai/kimi-code@2.7.0`。
- 标签对象：`dc94b1adec6d5aa10b0fc5cd7872d450eb16eeff`。
- 目标提交：`a5e355e2718a2ebf70d8229fa5a05fe35d5f98a1`。
- 上游发行版本：CLI `2.7.0`、Desktop `1.4.0`、KAP Server `0.3.1`；其余共同包以该提交的 manifest 为准，fork-only 包保持原版本。
- 本地起点：`main`，调查时 HEAD 为 `60a2cf0319`，工作区已包含未提交的 2.6.3 对齐、DeepSeek、任务续跑审计、记忆模块及 UI 改动。工作区内容而非 HEAD 单独构成需要保护的基线。

## 必须满足的行为

### R1 完整、可追溯的发行清点

1. 从固定目标的完整 Git 历史和文件树建立清单，覆盖 CLI、引擎、服务端、SDK、共享包、Desktop、Web、测试、构建与文档。
2. 不把 GitHub compare 最多 300 个文件的返回值当作完整差异；不把分叉发布分支的提交列表当作线性版本差异。
3. 每条适用改动必须有代码落点及可执行证据。已有移植先验证，不重复重写；纯结构差异与工具链翻译必须显式登记，不能以“Bun 不同”“本地没有对应文件”为由跳过用户能力。
4. 在固定目标中仍适用的旧 pending/partial 项同样纳入，不能只清点新标题。目标之外的新提交不自动混入。

### R2 保留现有 fork 能力与数据

1. 保留未提交工作、历史会话与配置，不以整文件覆盖或清理工作区实现合并。
2. DeepSeek 中途切换后的专属提示、普通执行任务的非终态结束审计、现有记忆模块边界、Operation Log、双语 UI、权限边界、Bun 打包及 GitHub 代理继续有效。
3. 既有 machine 引擎是保留的架构基线；上游 core 的新增行为和协议必须逐项对齐，纯目录/内核重排不强制替换整条执行链。最终交付是整仓功能与契约对齐，不宣称与上游逐文件相同。
4. 任何不能在此边界内保全的能力必须列为阻塞并说明原因，不默认为删除或完成。

### R3 后端、协议与客户端一致

1. 实现目标版本的 `/api/v1` 收敛、会话取消和紧凑状态/事件契约，同步所有仓内消费者；目标版本删除的入口按原始补丁与调用清单处理，不另造长期双协议实现。
2. SSH host 的连接、项目与会话聚合、重连及失败诊断完整落地，不只保留旧远程文件执行器。
3. KAP agent-to-agent HTTP wait/interactions/`kap.md`、Web JSON 启动输出、host product 标识及 Bash 会话/工作区 ID 按目标版本生效。
4. 补齐目标版本的预测提示、多行反馈、前台任务可见性、模型认证/输出上限、更新策略、WebBridge 和 Remote Control 修复；保留已落地的 2.6.3 请求正确性修复。

### R4 Desktop 和共享前端是真实源码交付

1. 导入 `apps/desktop`，以及 `packages/app-client`、`app-components`、`app-composer`、`app-core`、`app-i18n`、`app-markdown`、`app-ui`、`vite-preset`、`testkit`，纳入相应场景测试与图标工具。
2. 桌面聊天、会话恢复、模型切换、权限交互、任务/子代理、文件/Git、终端及内置浏览器不得因拆分后端而退化。
3. Web 从本仓 Desktop renderer 的 Web variant 构建，再通过现有同步工具更新 CLI `dist-web`；不能继续将其描述为仓外不可重建产物。
4. 保留上游 Desktop 与 Web 的边界，例如 Web variant 不伪造桌面终端或浏览器原生能力。

### R5 Desktop 使用 Bun

1. 本地基线使用 Bun `1.4.4`，不额外要求系统安装 `node`、`npm` 或 `pnpm`。合法的 `node:*` 模块导入可以由 Bun 原生兼容层执行，不按导入名字盲目重写。
2. 新增开发、测试和打包入口由 Bun 启动。单元测试使用 `bun:test`；桌面端到端场景保留 Playwright，由 Bun 驱动。
3. 引擎与 KAP 在 Bun 进程执行；Electron 只承担其必需的桌面宿主能力。不得在 Electron 中调用未提供的 `Bun.*`，也不得把引擎改回外部 Node 执行。
4. 发布形态包含同版本 Bun 后端可执行文件，从安装包内确定路径启动，不依赖用户 PATH 中碰巧存在的 CLI 或 Bun。
5. 开发态和打包态均有就绪、错误、取消、正常退出与异常退出清理契约，不能留下孤儿服务或悬挂请求。

### R6 版本、构建和验收

1. 共同包版本取自固定目标，依赖由现有 Bun 工具生成 `bun.lock`，冻结安装可重现；不运行自动升版或发布。
2. 新 workspace 真正参与测试、类型检查、构建和适用的 CI/Nix 文件集，不能仅放入目录却不被验收。
3. 在交付树上完成受影响测试、跨包协议场景、CLI bundle smoke、Web 构建和桌面端实际启动/退出验证，并构建本机平台的未签名桌面目录产物。
4. 文档与双语发行说明描述实际交付的功能和运行时边界。失败、平台跳过及未验证边界明确列出；未达到上述条件不能报告整版完成。

## 明确不在本次范围

- 提交、推送、开 PR、上传发行产物、发布 npm 或触发远端发布。
- 安装/替换系统中的 Kimi Code EXE、修改全局 PATH/注册表、自动导入真实浏览器登录态。
- 新增另一个桌面框架，或为“纯 Bun 窗口”重写上游全部 Electron 原生能力。
- 为对齐内部目录而无条件迁走 machine 引擎，或引入无人消费的第二套生产循环。
- 无关功能重构、提升历史测试配额、通过跳过测试掩盖移植缺口。
- 在 Windows 上声称已验证 macOS/Linux 的系统集成、签名与商店发布。

## 适用规范

编码、测试、i18n、同步台账及项目命令遵循 `CONVENTIONS.md`、`DEVELOP.md`、`.upstream/PLAYBOOK.md` 和目标子目录指引。本规格只约定本次对齐范围及新增运行时边界，不复制全局规则。
