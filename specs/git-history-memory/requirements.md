# Requirements — 把原始 git 部分蒸馏后注入上下文

## 目标

把**原始 git 历史**做**部分蒸馏**，把蒸馏结果直接注入模型上下文：让模型在动手改代码之前，就知道这个仓库的隐性约束——哪些文件总是一起改、某块代码最近被改过什么、某个改动为什么存在。

**范围只有一条：注入通道。** 输入是原始 git，输出是进上下文的蒸馏产物，中间没有"记忆存储系统"这一层。

明确不做的：写入型记忆（人/agent 记录偏好与决策、存在某个可编辑的存储里）。那是另一个课题；即使它存在，注入的也不是它。

## 受众

- 维护 `packages/agent-core-v2` 中 agent profile 组装、工具结果组装、reminder 通道的开发者；
- 使用者：在这个仓库里跑 agent 的人，**包括不主动调用工具的模型**。

## 目标函数：省 token 是错的目标

```
E[成本] = P(漏掉必改文件) × C(一次改错) + 注入量 × 1
```

| 项 | 量级 |
| --- | --- |
| 注入一份文件画像 | 800–1700 token |
| 改错一个文件 → 测试红 → 回读 3–5 个文件定位 → 再改 → 再跑测试 | 20K–60K token，3–10 轮 |

比值 **1:12 到 1:35**。由此得到三条总纲：

1. **不设 token / 字符上限。** 用便宜 12–35 倍的成本项去限制贵的成本项是算反了。
2. **优先保召回。** 漏掉导致失败回环；多给几个无关路径只是多扫一眼。
3. **只保留两条约束**：蒸馏出的内容必须真实（去团块）；病态情况不刷屏。

## 实测依据

1500 提交窗口，按时间切分（train = 较老 851 个可用提交，test = 最新 212 个，过滤 2–30 文件的提交）。指标：用 train 段统计预测测试提交的文件集，算 recall / precision。

**天花板 0.639**：测试提交里 36.1% 的文件在 train 段从未出现（新文件），任何历史方法都预测不到。

| 蒸馏形态 | 估计 token | 召回 | 精度 |
| --- | --- | --- | --- |
| 全局 top-500 共变对（score 排序） | ~1058 | 0.006（覆盖真实共变对） | — |
| 全局目录共变图 cap 400（score 排序） | 8992 | 0.039 | — |
| 3 个高精度伙伴（权重≥1 & score≥0.8） | ~20 | 0.103 | 0.651 |
| 1 组 change-group 文件列表 | ~860 | 0.385 | 0.088 |
| **3 组 change-group 文件列表** | **~1660** | **0.463** | 0.053 |
| 10 组 change-group 文件列表 | ~2950 | 0.497 | 0.040 |
| 最近一次变更压成目录 | 84 字符 | 0.647（**目录层**） | 0.202 |
| 前缀变更配方 topN=10 | 7.4 个路径 | 0.123 | 0.098 |

从 20 token 档升到 1660 token 档：多花 1640 token，召回 +36 个百分点。10 组档边际收益很小（+3.4pp 花 1290 token），所以取 3 组。

**目录压缩那一行不作主载荷**：0.647 只是目录层的完整度，文件层信息丢失；按成本模型，多给文件列表更值。

### 拆分的四次尝试（全是负结果，别重做）

| 拆法 | 召回 | 精度 | 无归属文件 |
| --- | --- | --- | --- |
| 共变图连通分量 score≥0.15 | 0.282 | 0.031 | 54.3% |
| 共变图连通分量 score≥0.20 | 0.221 | 0.147 | 60.5% |
| 共变图连通分量 score≥0.30 | 0.123 | 0.230 | 73.2% |
| 前缀变更配方 topN=10 | 0.123 | 0.098 | — |
| 目录共变图 cap 400 | 0.039（覆盖） | — | — |
| **原始提交（change-group）×3** | **0.496** | 0.044 | — |

三种拆法在各自最佳档位上都输给"单元 = 原始提交"。原因：这个仓库的变更跨切面（一个特性提交同时动实现、测试、i18n、文档），任何模块边界都会被跨过；54–82% 的文件在共变图里没有强边。

**结论：好的拆分不是"把提交拆细"，而是"单元 = 原始提交，键 = 文件路径"。**

### 去团块的实测必要性

未去团块时，`tools/review/build.zig` 及其 4 个 baseline 文件各报 **16 个伙伴**，`_base/lifecycle/disposer.ts` 等 8 个文件各报 **50 个伙伴**——全部来自两个机械提交：`26eaf0cd71 style: format the source trees with oxfmt`、`1ab19190e9 refactor: strip comments from agent-core-v2…`。

### 全局事实必须按 count 排序

| 门槛 | 对数 | 字符数 |
| --- | --- | --- |
| count ≥ 50 | 11 | 1085 |
| count ≥ 30 | 75 | 7434 |
| count ≥ 10 | 3020 | 344784 |
| count ≥ 5 | 48224 | 5993873 |

按 PMI 分数排的头部全是 `count = 1` 的巧合（score 恒为 1.0），所以 cap 400 对只覆盖 3.9%。`count ≥ 50` 的头部是真不变量：`i18n/locales/en.ts ↔ zh.ts`（63）、`docs/en/configuration/config-files.md ↔ docs/zh/…`（75）、`node-sdk/src/rpc.ts ↔ sdk-rpc-client-v2.ts`（59）。

### 成本实测（本仓库 3973 提交）

```
git log --format='%s'                    0.2s
git log -395 --name-only --format='%H'   0.9s
git log -395 --numstat --format='%H'     2.6s
git log --numstat --format='%H'         13.0s
```

## 需求

**R1 注入必须由系统驱动，不得要求模型主动调用任何工具。**
会话启动、轮次开始、文件进入视野三层触发全部自动。存在不主动调用工具的模型。

**R2 主通道是文件级条件注入（L3），挂在工具结果尾部。**
Read / Edit / Write 某个文件时把该文件的蒸馏结果附在工具结果里：自动、条件化、时机正确（见到文件后、编辑前）。

**R3 禁止按 token 或字符数裁剪注入量。**
不同模型分词器不同、计费口径不同，把 token 当切分单位既无技术依据也会因模型而异。

**R4 唯一的规模抑制：单组提交触碰文件数 >25 时只报摘要**（sha + subject + 日期 + 文件数 + 主要目录），不铺开列表。这类提交是批量操作，铺开没有信息量。

**R5 共变统计必须排除机械提交，并用与提交规模无关的相似度。**

- **排除触碰文件数 >25 的提交**（与 R4 同一门槛）：它们是格式化、去注释、批量重命名这类仓库级操作，会给所有被碰过的文件生成完全图。实测证据：`tools/review/build.zig` 及其 4 个 baseline 文件各报 **16 个伙伴**，`_base/lifecycle/disposer.ts` 等 8 个文件各报 **50 个伙伴**——全部来自 `26eaf0cd71 style: format the source trees with oxfmt` 与 `1ab19190e9 refactor: strip comments from agent-core-v2…`。
- **相似度用提交成员集上的余弦**：`score(x,y) = |A_x ∩ A_y| / sqrt(|A_x| · |A_y|)`，`A_x` 是触碰过 x 的提交集合。永远同行的两个文件得 1.0，**与提交规模无关**。
- 门槛：伙伴 `count ≥ 5 且 score ≥ 0.8`；不变量 `count ≥ 5 且 score ≥ 0.9`，按 count 降序取前 12。

**实施期修正（见 `progress.md`）**：原设计用 `w(pair) = 1/C(n,2)` 的加权公式。实施时发现该分值**随提交规模漂移**——两个永远同行的文件，在 2 文件提交里 score = 2.0，在 10 文件提交里只有 0.222，**最强的信号反而被门槛滤掉**。余弦公式在同一操作点给出几乎相同的实测结果（precision 0.407 / recall 0.149 / 平均提出 3.1 个 / 58.5% 提交命中），但门槛不再随仓库规模漂移。

**R6 L3 的主载荷是"最近 3 组 change-group 的文件列表"**，每组含 sha、subject、日期、文件列表。不压成目录。

**R7 L1 必须是结构化清单，不是散文。**
每行一条：`路径 | 最近变更 sha | intent(subject) | 变更强度`。模型能扫清单，扫不了散文。

**R8 每一项蒸馏结果必须带可执行的深挖指令。**
每组 change-group 带 `git show <sha> --stat` 形式的指针。**不新增工具**——模型本来就有 Bash。深挖是附加层，不是依赖：L1/L2 在没有深挖时依然完整。

**R9 L2 只在能从最近一条用户消息抽出文件路径时触发**，抽不到跳过，不做猜测式注入。

**R10 去重两级：文件级 + 变更组级。**
每文件每会话只注入一次；同一 change-group 的文件列表每会话只铺开一次，后续引用它的文件只输出 `see change <sha> above`。这条让累积量随会话收敛，是不按 token 裁剪的替代方案。

**R11 取数只允许窗口扫描，缓存命中时零 git 进程。**
只跑三条命令：`rev-parse HEAD`、`log -N --date=short --format=%H%x09%ad%x09%s`、`log -N --name-only --no-renames --format=%H`。禁止在启动/工具路径跑全历史 `--numstat`。索引按 HEAD 缓存。

**`--no-renames` 是必需的**：实测本仓库 1500 提交窗口下，带重命名检测的 `--name-only` 扫描耗时 **3.25s**，加 `--no-renames` 后 **0.54s**（6 倍），端到端从 3.45s 降到 0.84s。重命名检测是主要开销，而索引每次 HEAD 变化都要重算，这个成本必须压住。代价：改名文件在文件级视图里丢失改名前的历史（表现为"旧路径删除 + 新路径新增"）。

**R12 失败必须降级且留痕，不得阻塞工具调用。**
非 git 仓库 / git 缺失 / 超时 → 不注入（`log.debug`/`log.warn`）。索引损坏 → 丢弃重算。

**R13 注入文本是 C2 模型资产：英文、不翻译、不加 locale key。**

**R14 蒸馏结果必须可回溯到原始 git。**
每项带源提交 sha；人能 `git show <sha>` 复核。蒸馏是**投影**，不是事实源——**没有写入生命周期**，不能被"编辑"，也不会腐坏（源头即真相，缓存可重算）。

**R15 新增实验性 flag `git_memory`，默认关闭。**
flag 关闭时三层都不注入、不 spawn 进程、工具输出与今天逐字相同。

## 排除范围

- **不做写入型记忆系统**（可被 AI 编辑的偏好/决策存储）。那是另一课题；即使存在，注入的也不是它。
- **不做全局知识摘要作为知识载体**（只保留不变量清单这一小块）。
- **不做向量检索**（D9）。
- **不做 LLM 摘要**（D8）。
- **不做建模主动查询的工具作为主通道**（R1）。
- **不做"拆分提交成更小单元"**（四次尝试全负，见实测）。
- **不分析代码历史的 revert / 负知识**。
- **不读 forge API**（PR 描述、review 讨论）——需要凭据与网络，另开 spec。
- **不改 `<git-context>` 现有字段**、**不改 `promptPrefix` 机制**。


## 补充需求（引用核验后新增，R16–R19）

**R16 必须能弃权：蒸馏产物与当前上下文不相关时，完全不注入。**
CommitDistill 的检索器带**弃权阈值 θ=2.5**，对分布外查询主动弃答。本 spec 的对应规则：当目标文件在窗口内没有变更历史、没有满足门槛的共变、且不属于任何高计数不变量时，**整块不出现**——不是出现一个空块，也不是出现一条"无相关历史"的提示。宁可不注入，也别让模型学会忽略这一段。

**R17 检索类指标不等于任务效果，效果必须被实测。**
CommitDistill 在 12 条查询基准上 256 字符预算达到命中率 0.750（BM25 0.333，`git log --grep` 0.083），**但在 n=200 的时间旅行修 bug 对照实验里，四个臂（control / CommitDistill / CD-Hybrid / BM25）在主指标上没有任何统计可检测的提升**。

本 spec 因此不得以命中率、召回率作为"这个功能有用"的证据。这些指标只证明**信号被正确送达**。是否真的减少了漏改，必须做 flag 开/关的**行为对照**（见 T15）。

**R18 蒸馏产物必须逐字节可复现。**
同一个 `(repoRoot, headSha, window, version)` 必须渲染出逐字节相同的一段文本。这是 SCD（Structured Contextual Distillation）那个思路里可用且便宜的部分——我们的蒸馏产物本来就没有生成式步骤，不存在复述漂移。完整性链直接来自 git 自身的提交哈希链：每项带源提交 sha。

**R19 外部实现的描述以源码为准，不以转述为准。**
本轮核验已经发现一处广泛流传的错误描述（见 `design.md` §11.2）。凡是写进本 spec 的外部结论，必须标明是"读过源码"还是"只读了 README/转述"。

## 补充需求（SCD 核验后新增，R20–R22）

**R20 注入内容是不可信输入，必须按数据处理，不得按指令处理。**
蒸馏载荷里至少有三类**任何人都能写进仓库**的内容：commit subject、分支名、文件路径。它们会进系统提示与工具结果。

处理规则：
- 剥离控制字符与非打印字符（换行只保留结构性的换行）；
- 单条长度上限（subject 截断并标 `…`）；
- 全部放在明确的数据标记内（`<repo-memory>` / `<file-memory>`），标记内声明**内容是数据**；
- **注入文本不得包含祈使句**——不写"你必须先改这些文件""务必同步 zh 文档"。只陈述事实（"这 4 个文件在最近 5 次提交里一起被改"）。

理由：SCD §3.3 的论证——提示词是**建议性的**，可被覆盖、遗忘或通过注入绕过；且一个由本功能注入的祈使句，本身就是把"指令"交给了一个可能被污染的通道。价值必须来自**信息在场**，不来自模型服从一句祈使句。这与本仓库 C2 规则（注入给模型的文本是模型资产、不是 UI 文案）一致。

**R21 注入文本里不得出现原始浮点数。**
所有数值按固定格式输出：整数计数原样，比例与分数按固定小数位格式化。这样跨平台、跨运行都字节一致（R18 的落地细节）。索引里可以存浮点，但**渲染出来必须是稳定字符串**。

**R22 注入文本不得依赖模型"听懂了才生效"。**
每一条注入都必须能被模型**读出来**即用；不能出现"只有当模型把这条当成指令执行时才起作用"的措辞或结构。违反这条的设计会让整个功能的效果依赖模型的顺从度，而 CommitDistill 的对照实验已经说明：**这类效果的证据很难拿到**。
