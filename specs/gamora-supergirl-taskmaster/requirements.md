# Requirements — 关联记忆的完整优化计划

## 目标

让 `features/associativeMemory` 在**显著性、遗忘语义、抽象层影响力、状态卫生**四个维度上达到可测标准，延续"像人脑"的机制方向，不改变既有设计边界。

本文件只描述"要什么"。怎么实现见 `design.md`，怎么验收见 `tasks.md`。项目级规则（禁注释区、Bun 工具链、测试纪律）见仓库根 `AGENTS.md` / `CONVENTIONS.md`，此处不复述。

## 受众

- **开发者**：维护 `packages/agent-core-v2` memory feature 的工程师。
- **使用者**：跨会话长期工作、经验量超出上下文窗口、依赖被动联想召回的 agent 用户。

## 需求

### R1 — 显著性必须真的影响行为

`baseWeight` 目前是死字段：`pin` 把它加一，系统其余部分从不读它。要求把显著性做成**参与计算**的量：

- R1.1 显著性出现在召回打分里：两个其他条件相同的原子，`baseWeight` 高的排序不劣于低的。
- R1.2 显著性抵抗遗忘：同样年龄下，高显著性连接的权重衰减慢于低显著性。
- R1.3 显著性可观测：`explain` 的 trace 暴露每个节点的显著性，`list`/`stats` 可看到显著性的分布。

显著性来源仅限系统已存在的确定性信号（`pinned`、被强化次数、结构连通度），**不得**引入对自然语言的启发式判断。

### R2 — 淘汰语义与 R3 对齐

R3 把遗忘定义为"权重低于阈值"，而容量淘汰目前按"最旧优先"。要求统一为**可及性**排序：

- R2.1 淘汰候选按可及性升序选择；可及性由衰减后的权重、结构连通度、显著性共同决定。
- R2.2 在容量压力下，一个**连通度高、仍在使用**的旧记忆，必须优先于一个孤立的、从未被使用的较新记忆被保留。
- R2.3 淘汰继续保留墓碑语义与 `ids` 审计（已实现，不得回退）。

### R3 — 抽象层的影响力必须被量化并作出决定

概念与程序目前"能形成、能召回，但不占首"。要求先把问题变成可判定的，再决定是否改：

- R3.1 给出一个明确判据并实测：对**跨越 ≥3 个成员**的 cue，概念是否应进入首位。
- R3.2 若实测支持，则实现并保持三档召回门禁不退化；若不支持，则在工具描述中写明"概念是压缩节点，不保证优先"，并保持现状。
- R3.3 无论结论如何，都必须留下一条可复跑的断言，防止后续改动静默改变这一行为。

### R4 — 删除或启用死状态

- R4.1 `NoteRecord.atomIds` 若在本计划完成后仍无读者，必须删除（含写路径与类型）。
- R4.2 `Atom.baseWeight` 若被 R1 启用，保留并纳入测试；否则删除。
- R4.3 删除不得破坏 `rebuild`（它按笔记文本重训，不依赖 `atomIds`，须有测试证明）。

### R5 — 干扰必须被测量而不是假设

"模式分离"（相似但不同的记忆互相干扰）目前只有停用词与前缀过滤。要求先测量再决定：

- R5.1 构造"高度相似但结论不同"的语料，量化它们在召集中是否互相压制或误合并。
- R5.2 仅在测到可复现的干扰时才引入分离机制；否则记录为"未观察到干扰"，不写代码。

## 边界（明确不做）

- **不把 markdown 记忆作为关联图的输入**。系统与 `app/memory` 并存、互不干扰（既有边界）。
- **不让 LLM 进入写入或注入路径**。`specs/daredevil-tempest-domino/requirements.md` 已否决，本计划不推翻。
- **不做后台自动再巩固**。同一份 spec 的边界条款明确否决"后台自动写回"，因为无法判断是否真的矛盾。
- **不动 Markdown/graph 的存储合并**、**不引入 embedding provider**、**不做热路径性能改造**（本会话已完成）。
- **不改 i18n 文案键、不加 changeset、不动版本号**。
