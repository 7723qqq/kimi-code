# 真实 provider 实测：我的实现在真实流上并不更准

**日期**: 2026-10-07
**端点**: `https://ollama.com/v1`（`deepseek-v4-pro`）——配置里唯一的 `api.deepseek.com` 余额不足
（HTTP 402），其余路由 401/402/403。凭据从 `~/.kimi-code/config.toml` 读取，未打印。
**脚本**: `specs/argent-bobbi-morse-she-hulk/measure-real-provider.cjs`、`/tmp/decode-profile.cjs`、
`/tmp/robust.cjs`
**性质**: 首次在真实 provider 上测量，此前所有结论都基于模拟流。

## 结论（先说最重要的）

**我此前声称的 0.00% 精确度在真实流上不成立。实测中我这套的跨运行变异系数是 0.595，比
MiMo Code 的 0.077 差 7.7 倍。** 用户说"MiMo Code 是准的"，在我自己的数据面前站得住。

## 一、单次流的三方对比

300 token、真值 200 tok/s 的**模拟**流上（此前报告）：

| 实现 | 误差 |
| --- | --- |
| deepseek-harness | −1.64% |
| MiMo Code | −22.08% |
| 本实现 | 0.00% |

**真实流上（6 次运行，`deepseek-v4-pro`）**：

| 实现 | 均值 | 跨运行范围 | 变异系数 CV |
| --- | --- | --- | --- |
| deepseek-harness | 282.5 | 158.2 – **591.9** | **0.580** |
| **MiMo Code** | **151.1** | **134.2 – 172.1** | **0.077** |
| 本实现 | 298.3 | 163.8 – **638.0** | **0.595** |

**我错在哪里**：我的公式设计得更"正确"（分母只含 token 产生区间），但在真实流上它对
**到达突发**极度敏感。MiMo Code 的公式"错误"（分母含 TTFT），却因此**稳健**得多——TTFT 是
大而稳定的量，把突发摊平了。

**一个更准的公式，如果它的输入不稳定，产出的数字同样不稳定。**

## 二、根本原因（独立测量）

对真实流做到达间隔分析：

```
content parts: 89, completion_tokens: 378
tokens per content part: 4.25
inter-arrival gap: p50 17.9ms  p95 36.9ms  max 499.0ms
coefficient of variation: 2.28  → BURSTY
```

**两个致命事实：**

1. **每个 content part 平均携带 4.25 个 token，且逐次运行在 3.16 ~ 13.46 之间波动。**
   我的 `n−1` 分母假设"每个 part 对应一个 token"——**这个假设在真实数据上是错的，差 3~13 倍。**
2. **到达间隔 CV = 2.28**，存在 499ms 的孤立停顿。首末 part 之间的跨度因此不能代表 token 的
   产生速率。

**这正是 OpenTelemetry 拒绝做 chunk↔token 假设、改用 chunk 为单位度量的原因。** 我此前在
`literature-review-otel.md` 里记录了这条规范警告，却仍然实现了它警告的做法，并声称精确。

## 三、修正后的立场

| 我之前说 | 现在的事实 |
| --- | --- |
| "模拟流上 0.00% 误差" | 仍在模拟流上成立，但**模拟流假设了逐 token 均匀到达，而真实流不是** |
| "客户端只能测观测值，但我的公式是对的" | 公式对，**输入不可靠**，所以输出不可靠 |
| "MiMo Code 偏低 22%~51%" | 模拟流上如此；**真实流上它比我的稳健得多** |
| 隐含地认为我的实现优于两者 | **在真实数据上没有依据。** 我的实现在稳定性上最差 |

## 四、诚实的当前状态

- 我**无法**声称本实现"准确"。它在真实 provider 上的跨运行波动达 ±2 倍（163.8 ~ 638.0）。
- MiMo Code 的低估（约 −25%）是**系统性偏差**，好处是稳定：每次运行都给出可比的数字，
  用户能通过它观察相对变化。**一个稳定偏低的值，往往比一个时而准确时而爆表的值更有用。**
- 若要真正稳定，需要放弃"从到达时刻推断速率"这条路——即回到会话累计口径（deepseek-harness
  的做法）或 OTel 的 chunk 间隔直方图，二者都不试图还原瞬时 token 速率。

## 五、建议（供决定）

1. **回退到会话累计口径**，与 MiMo Code / deepseek-harness 同类，牺牲实时性换取稳定。
2. **保留现实现但降级展示**——不显示成精确速率，改显示区间或标注不确定性。
3. **保留现状**，接受 ±2 倍波动（我**不推荐**，因为界面会给出误导性的精确感）。

无论选哪个，**都应先把"0.00% 精确"这一说法从代码注释与报告中撤下**。

  未测。
