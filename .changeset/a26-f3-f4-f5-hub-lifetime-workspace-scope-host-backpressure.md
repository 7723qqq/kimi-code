Stop leaking an event hub per session/agent handle, refuse the unsupported workspace scope, and apply socket back-pressure to every host frame path (a26/F3 + a26/F4 + a26/F5 of the 2026-10-12 audit).

`session(...)`/`agent(...)` allocated an `EventHub` eagerly and pinned it in the klient's hub Set; the only removal path was `onIdle`, which a hub that was never subscribed to can never reach. Every call-only handle (`get()`, `update()`, `setTitle()` — the node-sdk issues one handle per RPC) therefore left a hub plus its captured scope alive until `klient.close()`. The hub is now memoized behind the handle's `events` getter, so allocation and tracking both start at the first subscription; the global hub stays eager (it is off the hot path), the idle/revive lifecycle is unchanged, and a lazily created hub is still torn down by `klient.close()`. `events` is a getter rather than a data property, so `{...handle}` no longer copies it — the repo reads `SessionHandle.events` only through the interface.

The memory dispatcher's `workspaceId` branch materialized a workspace instance via `IWorkspaceInstanceManager` and then resolved every service against the ROOT app scope, dropping the instance: callers got root data (or `REQUEST_INVALID`, depending on the service) while believing they had hit the workspace. An engine `WorkspaceInstance` is not a `ScopeLike` (no `accessor.get`), so the scope now fails fast with `REQUEST_INVALID` ("workspace scope is not supported by the memory transport") instead of silently degrading.

Finally, the IPC host only applied back-pressure to `stream_data`; `result`, `listen_result`, `error`, and `event` called `send`, which ignored `socket.write`'s return value. A client that stopped reading let the host's outbound buffer grow with the event rate (unbounded host memory). Those four paths now write through a throttled sender that waits for `drain` when the buffer is full; frames are queued FIFO behind one another so the bound actually holds against a synchronous burst (a bare per-frame `if (!write(x)) await drain()` does not), ordering is unchanged, and the handshake frames (`ready`, the `hello` verdict, `stream_end`/`stream_error`) stay eager because they are tiny and non-repeating.
