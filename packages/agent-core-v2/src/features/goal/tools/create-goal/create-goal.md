Create a durable goal that the runtime pursues across turns. Call it only when the user explicitly asks you to start a goal or work autonomously toward an outcome, or a host goal-intake prompt asks you to create one. Do not create a goal for greetings, ordinary questions, or requests without a checkable end state.

A goal has one authoritative completion condition. Put that condition in `completionCriterion`: it must be verifiable from observable evidence such as tool results, file contents, command output, or test results. `objective` supplies context for the work. If the request has no checkable condition, ask the user for one first; do not invent requirements. If the user clearly insists on a vague goal, warn once that it cannot be judged reliably, then create it with the closest condition the user actually stated.

Once the goal has a completion condition, the runtime asks the independent judge after every turn. Without one, the judge decides when you submit completion with `UpdateGoal`. The judge, not the assistant, decides completion; `UpdateGoal complete` only submits a completion request. Keep working until the judge accepts the condition, or until the goal is genuinely blocked.
